# BaNCS Forecast — transacciones, colas, procesos críticos y reposting

Pronóstico a 365 días de (1) **transacciones por hora** (Financiero y No Financiero), (2) **volumen por cola** y hilos
necesarios, (3) **duración y hora de inicio de los procesos críticos** del batch y (4) **reposting** (volumen, tiempo y
velocidad por tabla). Un solo dashboard HTML con cuatro pestañas, un solo Excel (`data/processed/ForecastBaNCS.xlsx`) y
una sola presentación (`presentacion/BaNCS_Forecast.pptx`).

Reposting sigue el mismo esquema que los demás modelos (limpieza → modelo → backtest → pronóstico, scripts en `model/`,
salidas en `data/processed/`). Se rehízo el 2026-10-22 desde cero, con datos hasta el día de negocio 2026-09-25. Reemplaza
al proyecto RepostingPredictorV2 (v4), que en los datos reales del 28-sep al 5-oct tenía 14,1 % de error de volumen; el
nuevo tiene 8,7 %.

## Cómo correr todo (desde la raíz, en este orden)
```
python model/limpieza_procesos.py        # procesos -> procesos_limpio.csv, calendario_laboral.csv (usa correcciones_fecha.csv y parches_ritm.csv)
python model/limpieza_tph.py             # TPH -> tph_limpio.csv, calidad_dias_tph.csv
python model/limpieza_colas.py           # colas -> colas_limpio.csv, colas_excluidas.csv (antes de pronostico_tph.py: de aquí salen los días de desvío)
python model/pronostico_tph.py           # pronóstico horario 365 d + bandas
python model/pronostico_procesos.py      # pronóstico de procesos 365 d + bandas
python model/pronostico_colas.py         # pronóstico por cola 365 d + bandas (después de pronostico_tph.py) ~3 min
python model/hilos_colas.py              # hilos por cola: referencia medida de DEP (AnalisisColas.xlsx) e indicadores -> hilos_*.csv
python model/backtest_dashboard.py       # predicciones de backtest (1, 7, 30, 90 d antes) ~5 min
python model/registros_contables.py      # registros contables reales + pronóstico -> registros_contables.csv
python model/picos_historicos.py         # (opcional) picos históricos -> picos_historicos.csv; generar_datos_dashboard y el Excel lo llaman solos
python model/limpieza_reposting.py      # reposting -> reposting_limpio.csv, reposting_excluidas.csv (después de limpieza_procesos.py: usa el calendario)
python model/backtest_reposting.py       # compara 4 métodos por tabla y variable -> backtest_reposting*.csv, reposting_ganadores.csv ~2 min
python model/pronostico_reposting.py     # pronóstico 365 d con el ganador + bandas -> pronostico_reposting.csv, pronostico_reposting_noche.csv (noche completa), bandas_reposting.csv
python model/generar_datos_dashboard.py  # -> data/processed/dashboard_data.json (incluye reposting)
python dashboard/build_dashboard.py      # -> dashboard/dashboard.html
python model/exportar_predicciones_excel.py  # -> data/processed/ForecastBaNCS.xlsx (abrir y guardar en Excel para fijar los valores de las fórmulas)
python model/comparativa.py              # -> data/processed/comparativa_pronostico_real.xlsx (pronóstico frente a los reales de data/comparacion/, en confiabilidad = 100 % - error)
```
`model/verificacion_ritm.py` compara los procesos contra el RITM (`verificacion_limpio.csv`).
`model/backtest_colas.py` compara los métodos por cola (con y sin cuadre); solo hace falta para revisar la elección de `METODO` (~5 min).

## Reglas de negocio clave
- **Día de negocio**: una ejecución que empieza antes de las 12:00 pertenece al día calendario anterior. El batch no corre fines de semana ni feriados de Ecuador. «Primer día» = primer día laborable tras un día no laborable.
- **Calendario**: feriados de Ecuador de la librería `holidays`. Cuando la ley traslada un feriado (martes → lunes; miércoles o jueves → viernes; sábado → viernes; domingo → lunes), la librería deja marcadas la fecha original y la «(observado)»: la original se descarta salvo en año nuevo, Navidad y Difuntos. Ajustes en `limpieza_procesos.py`: `FERIADOS_EXTRA` (puentes y suspensiones decretadas), `TRASLADO_NO_APLICADO` (traslados que el banco no aplicó: 9-oct-2025 no tuvo batch) y `NO_FERIADOS`. Revisarlos cada año.
- **Reposting, día de negocio**: el reposting del día hábil D corre en la madrugada de D+1. Hasta la primera corrida del 21-jul-2025 el archivo la registra con la fecha de ejecución (se asigna al día hábil anterior); desde la segunda corrida de ese día ya trae el día de negocio. Corridas en fin de semana o feriado: si el calendario del banco las marca como DEPURACION se excluyen; si el viernes anterior no tuvo corrida se le asignan; si no, se excluyen «por confirmar». Se excluyen también copias de otro día, depuraciones y pruebas anotadas, y TRX idénticos al día anterior en 2 o más tablas. Todo lo excluido, con su motivo, está en `reposting_excluidas.csv`.
- **Tipo de día operativo** (columna `tipo_op` de `calendario_laboral.csv`, la que muestran el dashboard y el Excel): las definiciones de `data/raw/Calendario_Operativo_Final_2024_2027.xlsx` del banco (día normal, primer día laboral, primer batch, fin de semana, feriado con su bloque de sábado y domingo), recalculadas sobre nuestro calendario. La DEPURACION del archivo no se usa: aplica solo al proceso de reposting (página futura); esos fines de semana cuentan como fin de semana normal, o como feriado si están pegados a uno. Revisado el 2026-10-21: coincide salvo en fechas donde los datos lo contradicen (2-3 ene 2025 y 9-oct-2025 tuvieron volumen de feriado y sin batch; 26-dic-2025 tuvo batch y volumen normal; oct y dic 2024 no tienen datos) y dos de 2027 fuera del horizonte. Se agregaron los feriados decretados del 30-abr-2026 (Decreto 354) y 20-nov-2026 (Decreto 507), que faltaban. `limpieza_procesos.py` imprime las diferencias cada vez que corre.
- **TPH**: las horas 23:00–04:59 ausentes son la ventana del batch (estado `batch`); los 14 días completos sin datos quedan vacíos. El pronóstico deja vacías las horas 23:00–01:59 de las noches de batch y no las suma al total diario.
- **Días de desvío**: los días en que el tráfico se desvía hacia las colas OMN/CI3 (17 hasta sep-2026, listados en `colas_excluidas.csv`) inflan el total de No Financiero (mediana +9%, hasta +48%). Se muestran como reales pero no entrenan el modelo de No Financiero (`modelo_tph.dias_desvio`). Financiero no se ve afectado.
- **Zonas del pronóstico** (días desde el último dato): 1–90 confiable, 91–180 intermedia, 181–365 indicativa.
- **Picos históricos** (`picos_historicos.py`, tarjetas de picos en las cuatro pestañas y hoja `Picos_historicos` del Excel): solo datos reales de entrenamiento (no los posteriores al 25-sep de data/comparacion/ de la comparativa). Transacciones: hora con más transacciones (TPS = TPH / 3600, promedio de esa hora) y día con más transacciones, en todo el historial y desde el cambio de nivel de No Financieras (`CAMBIO_NOFIN`, 12-mar-2026). Colas: sin días de desvío ni caídas, en todo el historial y desde el último cambio de enrutamiento de la cola (el gráfico solo dibuja este último). Contabilidad: noche con más registros contables y mayor ritmo (registros / duración de cfpd0111cm), en todo el historial (desde 13-oct-2025; hasta el 1-jun-2026 el primer día acumulaba el fin de semana) y desde la contabilidad diaria (`QUIEBRE_CFPD`, 2-jun-2026); una noche con ritmo más de 2 veces el siguiente mayor (18-feb-2026, duración incompleta) se descarta. Reposting: noche con más transacciones y noche más larga (la de la tabla más lenta), de la noche completa y por tabla; IMG4 e IMG8 también desde su cambio de nivel (7-sep-2026).
- **Comparar por tipo de día** (pestañas TXN, Colas y Procesos; en Colas el valor por hora solo existe en el tramo con detalle horario, fuera de él se compara el total del día): la base es el día elegido, o el primero del tipo desde ese día. Día normal = mismo día de la semana +1 a +4 semanas; primer día laboral (lunes o día después de un feriado) y fin de semana (sábado y domingo, o solo uno) = el de cada semana siguiente; primer día hábil del mes, último día hábil del mes y quincena (día 15, o el hábil anterior) = el de los meses siguientes; feriado = los cuatro feriados siguientes (de lunes a viernes). En Procesos no hay fin de semana ni feriado porque esos días no hay batch.

## Modelos
- **TPH**: LightGBM sobre log1p por serie, con variables de calendario y una variable de **régimen** (rampa 0→1 centrada en 2026-02-17: caída de ~20% de No Financiero, causa sin confirmar). Financiero suma una tendencia (Theil-Sen, +21% anual). La caída de No Financiero fueron en realidad cuatro escalones (2025-12-03, 2026-01-21, 2026-03-04, 2026-03-10); se probó reemplazar la rampa por ellos y no mejora el backtest, así que se mantiene la rampa.
- **Colas** (19; SDV se descarta por inactiva): media geométrica de LightGBM (calendario, con el histórico anterior a cada cambio de enrutamiento llevado al nivel vigente) y el perfil de las últimas 8 semanas; FN1, DP4, OLR y VST usan solo el perfil. Cada día se escala para que la suma de colas sea el total de TPH. Error diario a 90 días en backtest: 8,7% ponderado (5–9% en las colas grandes, ~14% en OMN y CI3). Los cambios de enrutamiento conocidos están en `ESCALONES` (`modelo_colas.py`); uno nuevo se agrega ahí. Los días de desvío temporal de tráfico (`colas_excluidas.csv`) no se usan para entrenar. El dashboard lleva detalle horario de todo el histórico real y de los primeros 90 días pronosticados (más allá, diario). El simulador de hilos funciona con cualquier día real o de esos 90 pronosticados; en el detalle por hora resalta la hora que exige más hilos.
- **Hilos por cola** (`hilos_colas.py`, sección de la pestaña Colas): los hilos activos por cola están en `HILOS_ACTIVOS` (consola de BANCS, oct-2026; máximo 99) y hay que actualizarlos ahí si cambian. DEP usa la fórmula de `AnalisisColas.xlsx` (hilos = máx(concurrencia P90, TPS P90 × W P90) escalado con la demanda), validada contra el Excel (14 hilos base, 26 con +90%, 33 a las 18:00); la muestra coincide con el CSV solo de 06:00 a 19:00. Las demás colas se estiman con su tiempo de servicio promedio (`Resumen_TXN_y_Tiempos_X_COLAS_*.txt`, un día, en segundos con 2 decimales: se usa el extremo alto del redondeo, +5 ms): carga media L = TPS × tiempo × 1,21 (la hora más lenta frente al promedio del día) y hilos = L + z·√L, con z medido en DEP (2,96 al P90; 12,91 para la concurrencia máxima). Aplicado a la propia DEP da entre 1,06 y 1,9 veces lo medido, nunca menos. Los códigos de dos letras del resumen se traducen en `CODIGOS`; se ignoran la fila sin código, 00–06 y TF. La demanda futura es el techo (P90) del pronóstico.
- **Procesos, subprocesos nuevos (oct-2026)**: bnccrn2dcm (~20 s) arranca tras lond0501cm con una espera de ~78 min; bncd0801 (~15 min) no sigue a la cadena y su inicio se pronostica por su cuenta (`PRED` en `pronostico_procesos.py`). La corrida de bncd0801 que se ejecuta el día 28 (o la última anterior si el 28 no hay corrida: domingo, lunes o feriado) lleva minutos extra de duración e inicio estimados con las corridas del 28 del histórico (`dias_28` y `efecto_28`; hoy unos +75 min y +52 min de inicio); esas corridas no entran a los efectos de calendario normales. cfpd0111cm sigue encadenado a lond0501cm (encadenarlo a bnccrn2dcm empeora el error del inicio). Entrenamiento hasta el día de negocio 2026-09-28 (`FIN_DIA_NEGOCIO`). Duraciones de 0 (inicio y fin en el mismo minuto) no entran al modelo de duración; una ejecución de 23 h de bnccrn2dcm se excluye como atípica.
- **Tiempos por cola**: promedio ponderado por transacciones de todos los reportes diarios; se descartan los registros con tiempos negativos (transacciones que cruzan la medianoche del domingo dan −86 400 s).
- **Procesos**: nivel de las últimas 8 semanas × multiplicador de «primer día»; inicio encadenado desde el Lote1. Un baseline simple superó a LightGBM.
- **Reposting** (`modelo_reposting.py`): por tabla se pronostican el volumen (TRX) y la velocidad (TRX por minuto); el tiempo es TRX / velocidad. Compiten cuatro métodos en un backtest de 11 orígenes mensuales (sep-2025 a jul-2026, hasta 180 días): estacional (últimos 4 mismos días de la semana × tendencia Theil-Sen acotada × factores de calendario), media de 60 días hábiles, LightGBM y la media geométrica de LightGBM y estacional. Gana el de menor error a 1–90 días (`reposting_ganadores.csv`): velocidad = media de 60 días en todas; volumen = IMG1 LightGBM, IMG2 e IMG4 mezcla, IMG7 estacional, IMG8 media de 60 días. Tablas activas: ≥ 50 % de días con volumen y media ≥ 200 en los últimos 60 días hábiles (IMG3, IMG5 e IMG6 quedan en 0). El cambio de nivel del 7-sep-2026 en IMG4 e IMG8 está en `ESCALONES` (el histórico anterior se lleva al nivel nuevo, como en colas) y su banda se amplía 1,5 veces.
- **Bandas 10–90%**: errores de backtest de origen móvil por tramo de horizonte; nunca se achican al crecer el horizonte. En la duración de procesos son simétricas (percentil 80 del error absoluto). `cfpd0111cm` no tiene backtests a más de 90 días: ahí usa la banda mediana de los otros subprocesos (`n=0` en `bandas_procesos.csv`).

## Limitaciones
Con 21 meses (TPH) y 12 meses (procesos) de historia, la estacionalidad anual se aprende de un solo año. Un cambio de nivel como el de marzo de 2026 no se puede anticipar. El pronóstico por cola supone que el enrutamiento vigente desde el 2026-03-10 se mantiene; sus bandas solo tienen backtests de hasta 180 días y, por el cuadre, las colas heredan los errores del total de TPH. Antes del 2026-07-27 no hay bitácora RITM para verificar fechas de procesos.
